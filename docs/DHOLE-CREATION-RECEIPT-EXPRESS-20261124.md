# Express delivery without extra Dhole APIs

The project owner deferred all three additional external APIs until the responsible person returns. Use the seven existing catalog GETs, approved bounded temporary mappings and existing creation POST. Independent Pricing verification is retained but not mandatory in the temporary mode.

After a controlled real pilot verifies the published creation contract (HTTP 200, exactly {"value":"nonempty UUID"} and the matching persisted request in Pricing), the operator may explicitly enable DholeSubmission:AcceptCreationReceiptEnabled=true with VerificationEnabled=false. For the pilot itself this policy must be explicitly enabled as part of the approved single-quote configuration to exercise customer notification; manually inspect the returned UUID in Pricing. It remains OFF by default. No automatic acceptance for historical receipts, other 2xx responses, missing/malformed UUID, timeout or failed POST. The durable creation_receipt_accepted_at_utc is set atomically with the original outcome only. State remains HttpAcceptedUnverified in DB; public/admin receipt reports AcceptedByProvider, not Confirmed. Independent GET can later upgrade the same row; it does not duplicate email. ConfirmationEmail pass uses the same atomic once-only reservation for either evidence type.

Apply additive schema with backup before activation. No flags, credentials, Compose, branches or production deployment changed. No live calls. Prior rollout notes requiring a new GET are superseded for the explicitly selected temporary receipt policy. Contact visibility and commercial review policy still require agreement; the pilot remains subject to explicit authorization.
